
\subsection{Virtual Knowledge Graph Mappings} \label{mappings}

The virtual knowledge graph mappings from the relational schema defined in \cref{relational} to the ontology covered in \cref{ontology} has been performed using the Ontop plugin for Protégé \cite{calvanese2016ontop}. This section lists and describes a representative subset of the developed mappings.

\subsubsection{IRI Generation}

The Ontop virtual knowledge graph fundamentally relies on generating unique, persistent Internationalized Resource Identifiers (IRIs) for every entity in the relational database. This is achieved using URI templates defined in the target clauses of the mappings, which bind primary keys from the relational schema to the namespace of the ontology. The templates \inlinecode{:district/\{code\}}, \inlinecode{:municipality/\{istat_code\}}, \inlinecode{:infrastructure-line/\{code\}}, \inlinecode{:infrastructure-node/\{code\}}, \inlinecode{:hazard-landslide/\{code\}}, and \inlinecode{:hazard-avalanche/\{code\}} are used in the developer mappings for the districts, municipalities, infrastructure lines, infrastructure node, landslide zones, and avalanche zones respectively. This guarantee that each physical or administrative object is represented as a distinct web resource. Note that both the infrastructure line and nodes as well as hazard zones are all collected into the different IRI temples. This is not strictly necessary, because as has been discovered during data profiling, the primary key space for the two tables is disjoint. However, making them use different IRI templates make the intention clearer and could possibly be used for some optimization. By consistently reusing these templates across all the mapping declarations, the virtual knowledge graph seamlessly merges data from disparate relational queries into a unified graph, allowing properties and classifications to be appended to the same entity incrementally.


\subsubsection{Simple Mappings}

The basic structural mappings directly instantiate the primary classes of the ontology and populate their basic data and object properties using straightforward SQL \inlinecode{SELECT} statements.

The below mappings \inlinecode{MAP-DISTRICT} and \inlinecode{MAP-MUNICIPALITY} instantiate the municipality and district elements. Aside from asserting the basic class membership, they also map scalar data properties such as the ISTAT code, area, and different localized string literals. Crucially, the mapping for the municipality leverages the existing foreign key \inlinecode{distr_code} to assert the \inlinecode{:belongsTo} object property, linking the municipality directly to its parent district's IRI.
Further, the mapping utilizes the spatial function \inlinecode{ST_AsText(geom)}  in the source SQL query to cast the PostGIS binary geometries into standard Well-Known Text strings and binds the result to the \inlinecode{:geometry} data property. The same pattern is used for all geometry carrying classes.

\subsubsection{Properties Requiring Relational Joins}

Because the elementary data analysis justified normalizing lookup tables to remove redundancies, the virtual knowledge graph mappings must bridge these normalized structures using SQL joins to construct some of the data properties that in the ontology have been assigned directly to the entities.

The \inlinecode{MAP-INFRASTRUCTURE-LINE-TYPE} and \inlinecode{MAP-INFRASTRUCTURE-NODE-TYPE} mappings use an inner join to retrieve the German and Italian descriptions from the normalized InfrastructureType table and insert them into the knowledge graph as \inlinecode{:typeNameDe} and \inlinecode{:typeNameIt} data properties to the existing \inlinecode{:infrastructure-line/\{code\}} and \inlinecode{:infrastructure-node/\{code\}} IRIs.

\subsubsection{Semantic Sub-classification}

To align the raw data with the ontology's orthogonal classification schemes for the infrastructure assets and hazard zones, some mappings are required instantiate semantic subclasses based on specific textual values found in the relational database.

For the infrastructure domain classification, these mappings use SQL \inlinecode{IN} clauses with a set of literals in the \inlinecode{WHERE} condition to group specific textual descriptions, for example "Methangasleitung" and "Umspannstation")into their respective functional ontology classes. Four different mappings exists for both the infrastructure lines and nodes, one for each of the ontology classes \inlinecode{:EnergyInfrastructure}, \inlinecode{:CommunicationInfrastructure}, \inlinecode{:WaterInfrastructure}, and \inlinecode{:WasteInfrastructure}. This dynamically asserts multiple inheritance, as an entity will be typed as both for example an \inlinecode{:InfrastructureLine} and an \inlinecode{:EnergyInfrastructure}. The mappings \inlinecode{MAP-INFRASTRUCTURE-LINE-ENERGY} and \inlinecode{MAP-INFRASTRUCTURE-NODE-WATER} show two representative examples for this kind of mapping.

\begin{figure}[ht!]
  \vspace*{-1mm}
  \textbf{\small\inlinecode{MAP-INFRASTRUCTURE-LINE-ENERGY}} \\
  \begin{minipage}[t]{0.50\textwidth}
    \centering
    \textbf{\scriptsize Source: SQL Query}
\begin{lstlisting}[language=SQL]

  AND name_de IN (
    'Methangasleitung', 'Hochspannungsleitung',
    'Mittelspannungsleitung', 'Fernwärmeleitung',
    'Methangasleitung - Bannstreifen',
    'Hochspannungsleitung - Bannstreifen')

A similar approach is taken for mapping of the hazard severity classification. Like for the infrastructure domain, these mappings translate the specific German string identifiers for danger levels into the defined ontology subclasses. This value-driven instantiation enables complex semantic queries based on danger severity without requiring users to know the exact string values used in the source database. Unlike the above mappings, these use direct equality because the mapping from string identifiers to ontology classes is one-to-one in this case. Only \inlinecode{MAP-HAZARD-LANDSLIDE-VERYHIGH} and \inlinecode{MAP-HAZARD-AVALANCHE-MEDIUM} are shown below, however, for all remaining combinations of danger level and hazard type  nearly identical mappings have been created.
