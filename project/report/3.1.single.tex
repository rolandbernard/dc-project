
\subsection{Single Column Analysis} \label{single}

Single column analysis has been performed for this project using both the YData Profiling Python library and the SCDP algorithm implementation for Metanome. The goal of this analysis is primarily to understand the type and distribution of data contained within the individual columns. As such it will influence for example the data type chosen for the corresponding attributes in the relational schema and ontology developed in \cref{relational} and \cref{ontology}. Below I include, in addition to some commentary about the results, also tables that include the most relevant information for each column of the various tables.

\Cref{tab:bz_infrastructure_line} shows the most important single column analysis results for each column of the \inlinecode{bz_infrastructure_line} table. The table contains a total of 47551 rows. We can operate that the table contains three columns that individually for a unique key, \inlinecode{ogc_fid}, \inlinecode{glm_id}, and \inlinecode{objectid}. \inlinecode{ogc_fid} is a sequentially increasing integer, going from 0 to 47551. Interestingly, \inlinecode{objectid} is stored as a real data type, with values such as "94188705.0", "94188707.0", or "94188708.0". However, all values are whole integers. The values of \inlinecode{glm_id} all follow the pattern \inlinecode{UrbanPlan-InfrastructurePlan-Network.<objectid>} where \inlinecode{<objectid>} is the integer value stored in the \inlinecode{objectid} column of the same tuple.

\inlinecode{istat_code}, \inlinecode{nda_link_de}, \inlinecode{nda_link_it}, \inlinecode{gem_text_d}, and \inlinecode{gem_text_i} all have 115 distinct values, indicating that they might contain related values. Manually inspecting \inlinecode{gem_text_d} reveals that it contains the names of municipalities, presumably the one the infrastructure line belongs to. \inlinecode{gem_text_i} contains the Italian name and \inlinecode{istat_code} some kind of identifier. \inlinecode{nda_link_de} and \inlinecode{nda_link_it} contain links that when followed lead to the Implementing rules to the land-use plan of the given municipality.

\inlinecode{code}, \inlinecode{bez_i}, and \inlinecode{bez_d} all have 11 distinct values. These values seem to indicate the type of infrastructure that is represented by this tuple, with the values in \inlinecode{bez_d} being the German name, those in \inlinecode{bez_i} the Italian name, and the values in \inlinecode{code} being an integer identifier of the type. Note that like with \inlinecode{objectid}, the values in \inlinecode{code} are represented as real numbers ending with ".0", meaning they all have integer values. The following are all possible values of \inlinecode{bez_d}: "Trinkwasserleitung", "Druckrohrleitung", "Abwasserleitung", "Schlammleitung", "Methangasleitung", "Hochspannungsleitung", "Mittelspannungsleitung", "Fernwärmeleitung", "Hochspannungsleitung - Bannstreifen", "Sonstige Leitungen", "Methangasleitung - Bannstreifen".

Finally, \inlinecode{geom} contains the geometry of the infrastructure line. Manual analysis reveals that the values are in the Well-Known Text format \cite{ISO_IEC_13249_3_2016} and all of them are of type \inlinecode{MULTILINESTRING}. \inlinecode{shape_len} seems to contain real values. Comparing them with the geometry in \inlinecode{geom} seems to indicate that \inlinecode{shape_len} might be the length of the infrastructure line.  \inlinecode{nda_text_de} and \inlinecode{nda_text_it} have a constant value of "Öffne" and "Apri" respectively. \inlinecode{codealt} and \inlinecode{blp} only contain missing values and are therefore not particularly interesting for this project.

The table \inlinecode{bz_infrastructure_node} contains columns that are very similar to those found in the \inlinecode{bz_infrastructure_line} table, as can be seen in \cref{tab:bz_infrastructure_node}. Like the table on infrastructure lines, here we also have the attributes \inlinecode{ogc_fid}, \inlinecode{gml_id}, and \inlinecode{objectid}, all of which are individually unique for all 4223 rows of the table. \inlinecode{objectid} still is an integer saved using a real number representation, and \inlinecode{gml_id} follows the pattern \inlinecode{UrbanPlan-InfrastructurePlan-Primary.<objectid>}.

The variables \inlinecode{code}, \inlinecode{bez_d}, and \inlinecode{bez_i} now have only 10 distinct values, and instead of representing a type of infrastructure line, they represent the type infrastructure node. The following are all 10 distinct values for \inlinecode{bez_d}: "Wasserfassung", "Kommunikationsinfrastruktur", "Umspannstation", "Kläranlage", "E-Werk", "Recyclinganlage", "Reservoir", "Fernheizanlage", "Pumpstation", "Müllentsorgungsanlage".

\inlinecode{istat_code}, \inlinecode{nda_link_de}, \inlinecode{nda_link_id}, \inlinecode{nda_text_de}, \inlinecode{nda_text_it}, \inlinecode{gem_text_d}, \inlinecode{gem_text_i}, \inlinecode{codealt}, \inlinecode{blp} have exactly the same values and properties as explained above for the \inlinecode{bz_infrastructure_line} table. Finally, the column \inlinecode{geom} still contains geographic information in the Well-Known Text format, however for this table all of them have type \inlinecode{POINT} instead of a multi-line.
