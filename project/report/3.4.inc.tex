
\subsection{Inclusion Dependency Discovery} \label{inc}

The BINDER algorithm implementation in Metanome has been used for inclusion dependency discovery in this project. The algorithm used by this implementation is following the divide and conquer-based approach presented in \cite{papenbrock2015divide}. The analysis has been run once over all five tables used in this project. Multi-column dependency discovery has initially been enabled, however, because it generates a very large number of 1024 different inclusion dependencies it became infeasible to analyze them. Therefore, the final evaluation uses the results of single-column inclusion dependency detection. The discovered multi-column inclusion dependencies have also been analyzed, but they largely do not contain any particularly relevant observations. This analysis can be used to find candidate for foreign keys between the different tables in the dataset which can be applied to the relational schema designed in \cref{relational}.

\Cref{tab:inc} shows all the single-column inclusion dependencies discovered between the tables in this project.
Among them are a number of coincidental inclusion dependencies between different dense identifiers that are purely valid because one of the ranges is smaller than the others. For example, all the inclusion dependencies involving the different \inlinecode{ogc_fid} columns belong to this category.
One notable inclusion dependency that has been discovered, and which will become a foreign key in the relational schema, is that from all the \inlinecode{istat_code} attributes in the infrastructure and hazard tables to that same column in the municipalities tables.
The columns \inlinecode{nda_text_it} and \inlinecode{nda_text_de} contain the same set of values in both of the infrastructure tables.
Similarly, the columns \inlinecode{id_gp}, \inlinecode{gem_id}, \inlinecode{name_d}, \inlinecode{name_i}, \inlinecode{desc_d}, \inlinecode{desc_i}, \inlinecode{bearbeitungstiefe}, and \inlinecode{gradodistudio} each contain the same set of values between the two hazard tables.
Interestingly, the analysis suggests that the set of municipality name in the infrastructure and hazard tables, such as those in the \inlinecode{gem_text_d}, \inlinecode{gem_text_i}, \inlinecode{name_i}, and \inlinecode{name_d} columns, are not exactly the same as the ones that are stored in the municipality table.

Looking at the multi-column inclusion dependencies, they contain many of the expected dependencies. For example both the inclusion dependency \inlinecode{avalanche}[\inlinecode{istat_code}, \inlinecode{gem_id}, \inlinecode{name_i}, \inlinecode{desc_d}, \inlinecode{name_d}, \inlinecode{desc_i}, \inlinecode{status_gzp}] $\subseteq$ \inlinecode{landslide}[\inlinecode{istat_code}, \inlinecode{gem_id}, \inlinecode{name_i}, \inlinecode{desc_d}, \inlinecode{name_d}, \inlinecode{desc_i}, \inlinecode{status_gzp}] and its reverse \inlinecode{landslide}[\inlinecode{istat_code}, \inlinecode{gem_id}, \inlinecode{status_gzp}, \inlinecode{desc_d}, \inlinecode{desc_i}, \inlinecode{name_i}, \inlinecode{name_d}] $\subseteq$ \inlinecode{avalanche}[\inlinecode{istat_code}, \inlinecode{gem_id}, \inlinecode{status_gzp}, \inlinecode{desc_d}, \inlinecode{desc_i}, \inlinecode{name_i}, \inlinecode{name_d}] are among them. Unfortunately, because a total of 473 multi-column inclusion dependencies were discovered by the algorithm, it is not feasible to extensively analyze them for further insights.
