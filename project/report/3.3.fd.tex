
\subsection{Functional Dependency Discovery} \label{fd}

Metanome using the HyFD algorithm implementation has been used for the discovery of Functional dependencies in this project. This implementation is based on the hybrid approach introduced in \cite{papenbrock2016hybrid}. As with the unique column combination discovery, also for this analysis NULL values have been configured to compare equal. The results of this analysis can be used to identify parts of the tables that can possible be extracted into separate relations in the design of the relational schema for \cref{relational}.

\Cref{tab:bz_infrastructure_line_fd} shows all the minimal functional dependencies discovered by the applied algorithm in the table \inlinecode{bz_infrastructure_line}. Aside from the two columns, \inlinecode{codealt} and \inlinecode{blp}, that are always missing and the three columns, \inlinecode{ogc_fid}, \inlinecode{gml_id}, and \inlinecode{objectid}, that are unique, we can still observe additional interesting information from the other functional dependencies.
First, it can be seen that \inlinecode{geom} functionally determines many other columns. This is quite intuitive because the geometry of two distinct infrastructure lines is likely not to be the same, unless they go along the same route. The functional dependency shows that all rows with the same geometry belong to the same municipality.
The functional dependency from \inlinecode{shape_len} to \inlinecode{nda_text_de} and \inlinecode{nda_text_it}, as well as those between \inlinecode{nda_text_de} and \inlinecode{nda_text_it} in both directions, can be explained by the fact that these two columns are constant except for the fact that they are missing in some rare cases.
Next, it can be observed that there are a number of functional dependencies related to individual municipalities. Municipalities can be identified by one of \inlinecode{istat_code}, \inlinecode{nda_link_de}, \inlinecode{nda_link_it}, \inlinecode{gem_text_d}, or \inlinecode{gem_text_i}. When a municipality is given, then in addition to these identifying columns also \inlinecode{nda_text_de} and \inlinecode{nda_text_it} are known to be present. This suggests a relational schema where these municipality related variables are extracted into a separate relation. This relation would most appropriately be use the \inlinecode{istat_code} as a primary key.
Finally, like in the case of the municipality, there are also three columns, \inlinecode{code}, \inlinecode{bez_i}, and \inlinecode{bez_d}, that all identify the kind of infrastructure that is represented by a row. These could also be extracted into separate relation with \inlinecode{code} as the primary key.

The functional dependencies discovered in the \inlinecode{bz_infrastructure_node} table are shown \cref{tab:bz_infrastructure_node_fd}. Largely the picture is very similar to that seen for the table \inlinecode{bz_infrastructure_line}.
Since this table is not missing municipality information for any row, the columns \inlinecode{nda_text_de} and \inlinecode{nda_text_it} are both also constant.
Interestingly, in this case the geometry in \inlinecode{geom} functionally identifies all other variables except for the identifiers. This indicates two distinct infrastructure nodes can be at the same location and with the same properties.

For the table \inlinecode{bz_hazard_landslide} a very large number of 255 functional dependencies has been discovered. However, many of them are not particularly meaningfully, because they use one or more from \inlinecode{geom}, \inlinecode{x_label}, and \inlinecode{y_label}. These columns are related to the location of the hazard area, and as such are already nearly unique. This means that adding additional columns quickly indices functional dependencies. For this reason, these functional dependencies have been removed from \cref{tab:bz_hazard_landslide_fd}.
In the remaining functional dependencies, aside from the unique or constant columns, a number of different interesting observations can be made. 
First, like with the infrastructure tables, this table contains information about the municipalities that are made up of the columns \inlinecode{istat_code}, \inlinecode{name_i}, \inlinecode{name_d}, and \inlinecode{gem_id}. Note that all of these except \inlinecode{gem_id} could be used to identify the municipality.
A similar relationship exists between the columns for the danger level, with the columns \inlinecode{code}, \inlinecode{pericolo}, and \inlinecode{gefahr} each being able to functionally determine the values of the others.
Regarding the type of landslide, there is a similar relationship between \inlinecode{processo} and \inlinecode{prozess}. However, in this case there is some inconsistency with regard to the \inlinecode{id_process}. Interactive analysis the of these columns shows that the reason for why this ID does not functionally determine the other two columns is that the values for \inlinecode{processo} and \inlinecode{prozess} are missing in very few cases. In these case a value for \inlinecode{id_process} is still present and not always the same.
A very similar situation is also present for the investigation depth, where \inlinecode{gradodistudio}, \inlinecode{bearbeitungstiefe}, and \inlinecode{id_gs} are related. However, because there are is one row with missing values for \inlinecode{gradodistudio} and \inlinecode{bearbeitungstiefe} but not \inlinecode{id_gs}, the latter does not functionally determine the former two.

The functional dependencies for table \inlinecode{bz_hazard_avalanche} are show in \cref{tab:bz_hazard_avalanche_fd}. Again, because in total the algorithm fount 281 different functional dependencies, \cref{tab:bz_hazard_avalanche_fd} removes some of them that contain \inlinecode{geom}, \inlinecode{x_label}, or \inlinecode{y_label} that are largely not insightful.
The overall structure of the functional dependencies is very similar to that for the landslide hazard zone dataset. The main difference is that because there are fewer missing values, it does not contain the misleading functional dependencies related to \inlinecode{id_process} and \inlinecode{id_gs}.
The columns \inlinecode{status_gzp}, \inlinecode{desc_i}, \inlinecode{desc_d}, and \inlinecode{id_phen} are all constant and the columns \inlinecode{ogc_fid}, \inlinecode{gml_id}, and \inlinecode{objectid} are all individually unique in the dataset.
The columns related to municipalities can clearly be identified as \inlinecode{istat_code}, \inlinecode{name_i}, and \inlinecode{name_d}. Each of these individually functionally determines the remaining two.
Similarly, the same dynamic exists for the avalanche type represented by \inlinecode{id_process}, \inlinecode{processo}, and \inlinecode{prozess}.
Further also the columns \inlinecode{code}, \inlinecode{pericolo}, and \inlinecode{gefahr} have the same relationship for the danger level.
Finally, \inlinecode{id_gs}, \inlinecode{gradodistudio}, and \inlinecode{bearbeitungstiefe} are all information about the investigation depth.

All the functional dependencies discovered by the algorithm in the \inlinecode{bz_admin_municipality} table are shown in \cref{tab:bz_admin_municipality_fd}. This table, as has already been discussed in \cref{ucc}, contains numerous unique columns.
Aside from the functional dependencies for these unique columns combinations, there are also two other interesting insights.
The column \inlinecode{health_district} functionally determines the value of the \inlinecode{health_region} variable.
Finally, the three different columns \inlinecode{distr_code}, \inlinecode{distr_de}, and \inlinecode{distr_it} represent the information about the the district the municipality belongs to. Each of them individually fully functionally determines the other two of them. These three could be extracted into a separate relation with a primary key of \inlinecode{distr_code} for the relational schema.
